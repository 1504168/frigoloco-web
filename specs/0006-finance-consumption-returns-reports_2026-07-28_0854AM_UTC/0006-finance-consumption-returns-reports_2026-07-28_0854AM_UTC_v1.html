Summary

Complete the Frigoloco finance module by adding the four report surfaces the product deck names as Phase-4 "Reporting" but the codebase has never built: a Consumption report (sold vs added, sell-through, waste), a dispatched-vs-added Reconciliation report (the derived successor to the removed legacy R9 verification), a monthly "by fridge" P&L dimension, and Excel export for the Weekly and Monthly views. Weekly P&L, monthly by client/supplier/category, the per-fridge GSV report, and the money (cents) layer already exist and are untouched.

Why

Imagine you run 40 smart fridges. Every week you need three answers: Did we make money? (P&L), What did people actually eat versus what we stocked? (consumption), and Does what we sent out match what physically ended up tagged in the fridges? (reconciliation). Today the app answers only the first. The other two live nowhere in the product - they were in the old two-workbook Excel process the whole rebuild is meant to replace, and the deck lists them as first-class Phase-4 artifacts alongside P&L.

The pain is concrete:

  • No consumption view. The legacy tool computed %Sold = Total Sold / Total Added per product and colored it (sell-through ≥90% good, <70% red) to drive forecasting and spot waste. The app stores every sale and every restock event but never surfaces this ratio. Without it, nobody can see which products are dead weight in a fridge.
  • No reconciliation. The legacy R9 "verification" route was deliberately removed on 2026-07-28, with an explicit note (both in operations.py and types.ts) that it must "return later as a derived, period-level report" comparing dispatch_lines against restock_events. That successor was never built, so the deliberate weekly=ADDED-basis vs monthly=DISPATCHED-basis discrepancy is invisible - you cannot tell whether a planned dispatch actually landed as valid tags.
  • Monthly P&L stops at client grain. You can slice a month by client, supplier, or category, but not by individual fridge - even though the legacy workbook's richest sheet was exactly a per-fridge monthly P&L, and a client can own many fridges with very different economics.
  • No export for the two main reports. Only the per-fridge GSV report exports to xlsx. Finance staff (a read-only role per the deck) cannot hand a weekly or monthly P&L to accounting without retyping it.

The cost of inaction: the app cannot yet replace the Excel workflow it was commissioned to kill. Finance stays in spreadsheets for consumption, reconciliation, and any exported report - defeating the core promise of the rebuild.

Explicitly out of scopeThe dual 50/50 global+fridge product-scoring model and CRUD for client service charges are real gaps too, but the user scoped this spec to the four reporting items above. They are noted here only so a reader does not expect them.

Background - the finance module as it stands today

Read this in dependency order: raw event tables first, then the service that aggregates them, then the router and UI. By the end you should be able to picture the whole current finance pipeline and see exactly where the four new reports plug in.

Step 1 - The raw event tables (the independent base)

Everything downstream is derived from three range-partitioned event tables plus dispatch lines. None of them store money totals; values are computed at query time by joining products.

  • restock_eventsevents.py:81 - one row per tag event. cols: fridge_id, product_id, action, tag_status, occurred_at. "Added" = action='added' AND tag_status='valid'. NO qty/price: added qty = COUNT(*), value = SUM(Product.purchase_price)
  • sales_eventsevents.py:42 - one row per sale. cols: fridge_id, product_id, sold_at, unit_price (cents), is_refunded. Sold qty = COUNT(*) where is_refunded=false
  • dispatch_linesoperations.py:189 - what was sent to a fridge. cols: fridge_id, product_id, delivery_date, qty, unit_purchase_price, unit_sales_price, vat_rate. Value = qty x (sales_ex_vat - purchase)
  • weekly_financialsoperations.py:304 - manual weekly inputs + fee snapshots (pos_fee_pct_snapshot, rfid_fee_snapshot)
The deliberate inconsistency you must preserveWeekly P&L uses ADDED (restock) value as its food-cost basis; monthly analysis uses DISPATCHED value. This is intentional legacy behavior, not a bug. The new reconciliation report exists precisely to make that gap visible and quantified, never to "fix" it.

Step 2 - finance_service.py aggregates events into P&L rows

This single service turns the raw tables into report data. The pieces the new work reuses:

  • Constants (all Decimal): VAT_DIVISOR = Decimal("1.06"), DEFAULT_POS_FEE_PCT = Decimal("0.09"), DEFAULT_RFID_FEE_RATE = Decimal("10") (cents). Fee rates are read from the settings table via _read_setting_decimal(session, "pos_fee_pct" | "rfid_fee_eur", default).
  • SQL expression helpers: _sales_ex_vat_expr() = coalesce(DispatchLine.unit_sales_price, Product.sales_price) / (1 + vat); _purchase_price_expr() = coalesce(DispatchLine.unit_purchase_price, Product.purchase_price).
  • Reusable group-by aggregators: _dispatched_food_margin(session, window, group_key) and _sales_and_items(session, window, group_key). The monthly dimensions are thin wrappers that pass Product.supplier_id or Product.category_id as the group key.
  • get_monthly_analysis(session, month, dimension) dispatches to _monthly_by_client / _supplier / _category and returns MonthlyAnalysisRead. Any dimension other than those three raises ApiError(422).
  • DateWindow dataclass (start/end) plus _month_window() and the weekly window helpers give every report its date bounds.

Proposed Solution

Add the four reports by extending the existing finance service, router, export service, and finance UI - no new tables, no new frameworks, no new patterns. Each report is a pure on-demand aggregation over event tables that are already indexed and date-windowed. This is chosen over any stored/snapshotted design because the model note for the removed R9 explicitly mandates "computed on demand ... NOT stored", and because the existing monthly analysis already proves the derived-on-read approach performs acceptably at current scale.

Metric definitions (the exact math)

MetricDefinition
Added qtyCOUNT(restock_events) where action='added', tag_status='valid', occurred_at in [from, to)
Sold qtyCOUNT(sales_events) where is_refunded=false, sold_at in [from, to)
Sell-through %sold_qty / added_qty (null when added_qty = 0), quantized to 4 dp
Unsold qtymax(added_qty - sold_qty, 0)
Unsold %unsold_qty / added_qty (null when added_qty = 0)
Dispatched valueSUM(dispatch_lines.qty x coalesce(unit_purchase_price, Product.purchase_price))
Added valueSUM(Product.purchase_price) over the added restock rows
Value deltadispatched_value - added_value (cents; signed)

Date-window convention (both reports): the from and to query params are calendar dates and the window is inclusive of both. It is implemented as a half-open timestamp interval [start_of(from), start_of(to + 1 day)) - so the [from, to) notation in the table above refers to that exclusive upper timestamp, and every event on the to date is counted. Restock/sales use occurred_at/sold_at; dispatched value uses delivery_date.

Trade-off Analysis

Decision 1 - Derived-on-demand vs stored report tables

Derived on demand
Chosen

Every report is a query over existing event tables at request time.

  • Zero schema changes / migrations
  • Always consistent with source events
  • Matches the removed-R9 mandate ("NOT stored") and the existing monthly pattern
  • Recomputes each call
Stored / snapshot tables
Rejected

Materialize weekly/monthly report rows into new tables.

  • Fast reads
  • Point-in-time close-out
  • New tables + migration + a refresh job
  • Staleness / drift vs events
  • Contradicts the explicit design note

Decision: Derived on demand. At 40 fridges (target 200) over a single period the aggregations are small and date-windowed on partition keys. Revisit only if a report must span many months at product grain and profiling shows a real problem - then a materialized view is the first escalation, not a hand-rolled table.

Decision 2 - Monthly "by fridge" as a new dimension vs reusing the GSV fridge report

New fridge dimension in monthly
Chosen

Add _monthly_by_fridge alongside client/supplier/category, same row schema.

  • One consistent monthly P&L surface, one export path
  • Reuses _dispatched_food_margin / _sales_and_items
  • Full P&L columns (fees, logistics), matching the legacy per-fridge sheet
  • Needs a per-fridge attribution rule for client-level fee/logistics
Extend the GSV fridge report
Rejected

Bolt monthly P&L onto the existing per-fridge GSV endpoint.

  • Already fridge-scoped
  • GSV is a single-fridge added-basis report, not a multi-fridge P&L row set
  • Different columns, different UI, no month tabs

Decision: New dimension. It slots into the existing get_monthly_analysis switch and the MonthlyAnalysisRow schema, so the monthly UI, columns, compare control, and the new export all work with one added tab.

Decision 3 - xlsx builder: reuse Polars+openpyxl vs a generic exporter

Reuse the fridge-report pattern
Chosen

Two new builders in report_export_service returning ExcelDocument.

  • Identical style/format to existing export
  • Polars for the table, openpyxl for the styled summary - already a proven pair here
  • Some boilerplate per report
Generic row-to-xlsx helper
Rejected

One abstract exporter for all report shapes.

  • Less duplication long-term
  • Speculative abstraction over 2 call sites
  • Harder to give each report its own summary block

Decision: Reuse the concrete pattern. Two call sites do not justify an abstraction (Simplicity First); each report keeps a tailored summary header.

Phase 2 - Consumption report

Step 2.1 - create backend/app/services/consumption_service.py. Import the shared window helpers and enums from finance_service (or a shared module). Signature and logic:

def get_consumption(
    session: Session,
    date_from: datetime.date,
    date_to: datetime.date,
    group_by: str,
) -> ConsumptionData:
    window = DateWindow(_start_of(date_from), _start_of(date_to + one_day))
    group_col, name_map = _resolve_consumption_grouping(session, group_by)  # 422 on bad value
    added = _added_counts(session, window, group_col)   # {key: int} COUNT(restock_events added/valid)
    sold  = _sold_counts(session, window, group_col)    # {key: int} COUNT(sales_events not refunded)
    rows = []
    for key in sorted(set(added) | set(sold), key=lambda k: name_map.get(k, "")):
        a, s = added.get(key, 0), sold.get(key, 0)
        st = (Decimal(s) / Decimal(a)).quantize(_FOUR_PLACES) if a else None
        unsold = max(a - s, 0)
        up = (Decimal(unsold) / Decimal(a)).quantize(_FOUR_PLACES) if a else None
        rows.append(ConsumptionRowData(key, name_map.get(key, ""), a, s, unsold, st, up))
    return ConsumptionData(date_from, date_to, group_by, rows)

Group columns: product → Product.id (name = Product.name); fridge → RestockEvent.fridge_id / SalesEvent.fridge_id (name = Fridge.friendly_name); category → Product.category_id (name = Category.name). Added counts filter action == RestockAction.added, tag_status == TagStatus.valid, occurred_at in window; sold counts filter is_refunded.is_(False), sold_at in window.

def get_reconciliation(session, date_from, date_to, group_by) -> ReconciliationData:
    window = DateWindow(...)
    group_col, name_map = _resolve_recon_grouping(session, group_by)  # total|fridge|product|category
    disp = _dispatched_qty_value(session, window, group_col)  # {key: QtyValue}
    add  = _added_qty_value(session, window, group_col)       # {key: QtyValue}
    rows = []
    empty = QtyValue(qty=0, value_cents=0)
    for key in _ordered_keys(disp, add, name_map):
        d = disp.get(key, empty); a = add.get(key, empty)
        rows.append(ReconciliationRowData(
            key, name_map.get(key, ""),
            d.qty, d.value_cents, a.qty, a.value_cents,
            d.qty - a.qty, d.value_cents - a.value_cents))
    return ReconciliationData(date_from, date_to, group_by, rows)
