Summary

Re-create the legacy "Create Individual Dispatch" file output in the new stack: when an operator confirms an individual dispatch, the backend generates a per-fridge driver delivery workbook (.xlsx) and the browser downloads it automatically - reproducing the file the old Excel + Power Automate flow used to email, minus the email step (which lands in Phase 2).

ScopeDispatch export - 1 new service, 1 new endpoint, 1 UI hook
Files2 new · 3-4 modified
Effort~1 day
RiskLow (read-only export; no stock/transaction change)
Phase 2 (later)Per-supplier emailing

Why

Imagine you are the operator on dispatch day. You have decided exactly how many of each product each fridge should receive. In the old Excel workbook, you clicked one button - "Create Individual Dispatch" - and two things happened: the system recorded what was leaving the warehouse, and a neat delivery file appeared and got emailed out, one page per fridge, listing product, supplier and quantity, with the fridge's delivery address and instructions at the top. The driver (and whoever needed it) received a ready-to-use sheet.

In the new web app, that same button exists - but it only does the first half. Confirming an individual dispatch snapshots prices and writes the negative stock movements correctly. Then it stops. No file is produced, nothing is downloaded, nothing is emailed. The entire "turn this dispatch into a per-fridge delivery document" capability was never ported from the legacy Office Scripts.

Where the legacy behaviour actually lived The old Office Script never sent mail itself. It POSTed a JSON payload to a Power Automate webhook (updatedispatchfile); a second script (Update Individual Dispatch (From PA)) built the per-fridge workbook, and Power Automate attached and emailed it. The recipient logic lived entirely inside Power Automate and is not in any code we have - so it cannot be recovered, only re-designed. This is the key reason emailing is split into a later phase.

The problem: operators lose the single-click "confirm and get the delivery file" workflow they relied on. Today they would have to reconstruct a delivery sheet by hand from the grid - error-prone and slow - or the drivers get nothing. The cost of inaction is a daily manual workaround for a document the system already has all the data to produce.

This spec restores the file output and keeps the one-click UX: confirming an individual dispatch again produces the per-fridge workbook and downloads it. Automated emailing (now per supplier, a deliberate change of grouping) is scoped as Phase 2 once recipients and a mail provider are decided.

Background - the current system, in dependency order

The dispatch feature is the third stage of a keyed planning pipeline. Everything keys on the triple (iso_year, week_no, day_name). Here is what exists today, most-independent piece first, so the whole current flow is clear before we change anything.

  1. Planning grid & reference data - frontend/src/pages/ops/dispatch/DispatchPage.tsx renders a fridge (columns) x product (rows, grouped by category) grid. It already has, per product, the supplier identity and prices via useProductMeta (ops/lib/grid.ts): productName, code, supplierId, supplierName, purchasePrice, .... So the UI is not missing any data - it simply has no export action.
  2. Dispatch SAVE (planned) - POST /api/v1/dispatches/save -> dispatch_service.save_planned(). Writes/replaces dispatch_lines only. Status draft/saved. No stock effect, no price snapshot. This is the plan.
  3. Create Individual Dispatch (the stock-writing path) - POST /api/v1/dispatches/create-individual?year&week&day_name&force -> dispatch_service.create_individual_by_key() -> confirm_dispatch(). In one transaction it locks the dispatch, snapshots prices onto each line (unit_purchase_price, unit_sales_price incl. per-fridge overrides, vat_rate), writes one negative StockMovement per line, and flips status to dispatched. The DB non-negativity trigger is the source of truth (violations surface as HTTP 409 stock_blocked). This is the only path that writes stock_movements. It returns JSON ConfirmResult{dispatch_id, status, movements_created}.
  4. The data the file needs is all joinable. Per dispatch line: DispatchLine.qty; product via product_id -> Product.name/code; supplier via Product.supplier_id -> Supplier.name (nullable, LEFT JOIN); category via Product.category_id -> Category.name + Category.dispatch_print_order (the fixed "driver delivery sheet" order); fridge via DispatchLine.fridge_id -> Fridge.friendly_name, husky_id, husky_name, delivery_address, delivery_instructions. Batch metadata from Dispatch: delivery_date, iso_week, weekday. Models define FK columns but no SQLAlchemy relationship() - joins are written explicitly.
  5. A proven Excel export pattern already exists - backend/app/services/report_export_service.py exposes the ExcelDocument dataclass (constructor fields filename and content: bytes; media_type is a read-only @property returning the xlsx MIME type, not a field) and builds the finance fridge report with Polars + openpyxl. It is streamed by GET /api/v1/finance/fridge-report/export.xlsx in routers/finance.py via a raw Response with a Content-Disposition attachment header. The frontend downloads it with the generic downloadFileFromApi() helper in frontend/src/pages/finance/utils.ts. All three are reusable.

Proposed Solution

Approach: add a read-only export that regenerates the per-fridge workbook from the persisted dispatch lines, exposed as a GET endpoint, and have the dispatch page call it automatically the moment "Create Individual Dispatch" succeeds. This was chosen over streaming the file directly from the confirm endpoint because it keeps the confirm contract (JSON ConfirmResult with its stock_blocked error handling) untouched, and because a regenerable GET makes the file idempotent, re-downloadable, and a clean seam for Phase-2 emailing.

Trade-off Analysis

Decision 1 - How is the file delivered to the operator?

Download from UI (auto on confirm)
Chosen (Phase 1)

Backend generates; browser downloads automatically when confirm succeeds.

  • No mail infra or recipient list needed
  • Preserves one-click UX
  • Operator forwards as needed
  • Not automatic delivery to third parties (that is Phase 2)
Email from backend
Phase 2

Backend emails the file via a mail provider.

  • Fully automated like the old flow
  • Needs mail credentials + recipient policy
  • Recipient logic was lost with Power Automate
Re-use Power Automate webhook
Rejected

Re-POST to the legacy updatedispatchfile flow.

  • Reuses existing PA recipient setup
  • Keeps a hidden, un-versioned dependency on PA
  • Against the "port off Excel/PA" direction of the project

Decision: ship download-from-UI now (chosen in the kickoff Q&A: "Download now, email later"). Backend emailing is deferred to its own spec because the legacy recipient logic is unrecoverable and mail infra is a separate concern. We reject re-using Power Automate because it re-introduces exactly the hidden dependency this project is migrating away from.

Decision 2 - Stream from confirm, or a separate GET endpoint?

Separate regenerable GET
Chosen

Confirm stays JSON; a GET rebuilds the file from persisted lines.

  • Confirm contract + stock_blocked handling untouched
  • Idempotent, re-downloadable
  • Clean seam for Phase-2 emailing
  • Second round-trip after confirm (negligible)
Return bytes from confirm
Rejected

Confirm streams the workbook directly.

  • One round-trip
  • Breaks the JSON error envelope (stock_blocked, past_date_requires_force)
  • No re-download without re-confirming

Decision: the GET endpoint. Coupling ("generate as part of Create Individual Dispatch") is honored at the UX layer - the frontend fires the download in onSuccess - not by overloading the transactional endpoint.

Decision 3 - Excel engine: Polars or openpyxl?

openpyxl (cell-level)
Chosen

Direct cell writing for per-sheet header blocks + category groups + borders.

  • Full control over multi-block layout the legacy file used
  • One worksheet per fridge is trivial
  • More imperative than a single table write
Polars write_excel
Rejected here

Renders one flat table per sheet.

  • Concise for flat tables (used by finance report)
  • Cannot express header block + interleaved category headers cleanly

Decision: openpyxl, consistent with the "decorate" pass already in report_export_service.py. We reuse that module's ExcelDocument dataclass rather than defining a second one (DRY). Global rule note: Polars is the default for Excel, but the explicit exception is rich formatting/merged/multi-block layouts - which is exactly this file.

"""Excel export builder for the per-fridge individual-dispatch delivery file.

Regenerates the legacy "Create Individual Dispatch" workbook from the persisted
dispatch lines: one worksheet per fridge, line items grouped by category in
dispatch_print_order, columns Product / Supplier / Quantity, with a per-sheet
delivery header block. Read-only; writes nothing.
"""

from __future__ import annotations

import io
from dataclasses import dataclass, field
from datetime import date

from openpyxl import Workbook
from openpyxl.styles import Font
from sqlalchemy import select
from sqlalchemy.orm import Session

from app.models.master import Category, Fridge, Product, Supplier, Client
from app.models.operations import Dispatch, DispatchLine
from app.schemas.masters import api_error
from app.services.report_export_service import ExcelDocument

_HEADER_FONT = Font(bold=True)
_TITLE_FONT = Font(bold=True, size=14)
_MAX_SHEET_NAME = 31  # Excel hard limit
_DAY_NAMES = (
    "Monday", "Tuesday", "Wednesday", "Thursday", "Friday", "Saturday", "Sunday",
)


@dataclass(frozen=True)
class DispatchFileLine:
    category_name: str
    category_print_order: int
    product_name: str
    supplier_name: str | None
    qty: int


@dataclass
class DispatchFileFridge:
    friendly_name: str
    husky_id: str
    husky_name: str | None
    delivery_address: str | None
    delivery_instructions: str | None
    lines: list[DispatchFileLine] = field(default_factory=list)


@dataclass(frozen=True)
class DispatchFileData:
    iso_week: int
    weekday: int
    delivery_date: date
    fridges: list[DispatchFileFridge]

    @property
    def day_name(self) -> str:
        return _DAY_NAMES[self.weekday - 1]


def build_dispatch_file_xlsx(session: Session, dispatch_id: int) -> ExcelDocument:
    """Build the per-fridge dispatch workbook for a dispatch id."""
    data = _load_dispatch_file_data(session, dispatch_id)
    return _render_workbook(data)

The query joins lines to product/supplier/category/fridge, filters qty > 0, and orders by fridge then Category.dispatch_print_order then product name. Supplier and client are LEFT joins (both nullable). Delivery address falls back fridges.delivery_address -> clients.location -> None.

def _load_dispatch_file_data(session: Session, dispatch_id: int) -> DispatchFileData:
    dispatch = session.get(Dispatch, dispatch_id)
    if dispatch is None:
        # Follow the router's existing convention (same as get_dispatch()):
        # raise api_error(404, ...), which propagates to an HTTP 404.
        raise api_error(404, "not_found", "Dispatch not found", {"dispatch_id": dispatch_id})

    rows = session.execute(
        select(
            Fridge.friendly_name, Fridge.husky_id, Fridge.husky_name,
            Fridge.delivery_address, Fridge.delivery_instructions,
            Client.location.label("client_location"),
            Category.name.label("category_name"),
            Category.dispatch_print_order,
            Product.name.label("product_name"),
            Supplier.name.label("supplier_name"),
            DispatchLine.qty,
        )
        .join(Fridge, Fridge.id == DispatchLine.fridge_id)
        .join(Product, Product.id == DispatchLine.product_id)
        .join(Category, Category.id == Product.category_id)
        .outerjoin(Supplier, Supplier.id == Product.supplier_id)
        .outerjoin(Client, Client.id == Fridge.client_id)
        .where(DispatchLine.dispatch_id == dispatch_id, DispatchLine.qty > 0)
        .order_by(
            Fridge.friendly_name,
            Category.dispatch_print_order,
            Product.name,
        )
    ).all()

    # group rows -> DispatchFileFridge (address = delivery_address or client_location)
    ...
Grouping detail Build an ordered dict keyed by friendly_name. For each row, set the fridge header fields once, then append a DispatchFileLine. Because the query is ordered, categories and products already arrive in print order - no re-sorting needed in Python.

Step 1.2 - workbook builder. One sheet per fridge; write the header block, then per-category blocks with a bold category header and Product/Supplier/Quantity rows. Truncate + de-duplicate sheet names to satisfy Excel's 31-char / uniqueness rules.

def _render_workbook(data: DispatchFileData) -> ExcelDocument:
    workbook = Workbook()
    workbook.remove(workbook.active)  # drop the default empty sheet
    used_names: set[str] = set()

    for fridge in data.fridges:
        sheet = workbook.create_sheet(_safe_sheet_name(fridge.friendly_name, used_names))
        _write_fridge_header(sheet, fridge, data)
        _write_fridge_lines(sheet, fridge)

    out = io.BytesIO()
    workbook.save(out)
    filename = f"Week {data.iso_week} {data.day_name} Dispatch.xlsx"
    return ExcelDocument(filename=filename, content=out.getvalue())


def _safe_sheet_name(name: str, used: set[str]) -> str:
    base = name[:_MAX_SHEET_NAME]
    candidate, suffix = base, 2
    while candidate in used:
        tail = f" ({suffix})"
        candidate = base[: _MAX_SHEET_NAME - len(tail)] + tail
        suffix += 1
    used.add(candidate)
    return candidate

@router.get("/{dispatch_id}/dispatch-file.xlsx")
def export_dispatch_file(
    dispatch_id: int,
    session: Session = Depends(get_db),
) -> Response:
    """Stream the per-fridge individual-dispatch workbook as an .xlsx."""
    document = dispatch_export_service.build_dispatch_file_xlsx(session, dispatch_id)
    return Response(
        content=document.content,
        media_type=document.media_type,
        headers={
            "Content-Disposition": f'attachment; filename="{document.filename}"'
        },
    )
Route ordering Register this alongside the other /{dispatch_id}/... routes. A literal segment (dispatch-file.xlsx) after the {dispatch_id} path parameter does not collide with the bare GET /{dispatch_id}. For an unknown id the service raises api_error(404, "not_found", ...) - the same convention get_dispatch() already uses - which propagates to HTTP 404, so no new exception type is introduced and the router needs no try/except. Import note: routers/dispatches.py currently imports only Depends, Query, status from FastAPI and get_db from app.db; add from fastapi.responses import Response (as routers/finance.py does) and import the new dispatch_export_service module.
